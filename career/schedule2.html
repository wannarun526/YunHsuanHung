1. 為什麼改成 top-down

我的強項在最上層（Python、REST、Linux、正式環境除錯），由下往上學，等於前 6 個月都在離強項最遠的地方打轉，而且一直沒有東西可以給面試官看。

由下往上的問題

  • K&R、CS:APP 讀了幾個月，還不知道這些東西在伺服器的哪裡用到，動機容易掉
  • 第一個能放上履歷的作品要到第 4 個月（bootloader），能投的職缺要到第 8–9 個月
  • 學了很多「之後可能用到」的東西，真正用到時又忘了

由上往下的好處

  • 第一個螺旋就用到強項：Python 加 Redfish 做伺服器診斷工具，對應鴻海高雄 Server Diagnostic 職缺「經歷不拘、重視 Python／Linux 與 debug 能力」
  • 每一層都是「為了解決眼前的問題」才往下學，記得牢
  • 大約 2–3 個月就有可以投的作品，邊學邊用面試回饋校正方向

但要守住的底線

  • 韌體面試一定考 C 手寫題，這是由下往上的硬功夫，不能只靠專案「順便學」
  • 所以保留一條補強軌（30%）：K&R、CS:APP、手寫題照進度走，只是章節順序改成「下一個螺旋要用到的先讀」
  • K&R 已經讀到第 3 章，不浪費，繼續往下讀

2. 學習方法：一個螺旋怎麼走

每個螺旋都有一個「看得到的成品」。成品做出來之前，按照下面五步反覆走。

步驟做什麼例子（螺旋 2：OVMF 開機）
① 先跑起來照官方文件把東西跑起來，先不求懂在 QEMU 用 OVMF 開進 UEFI Shell，把 debug log 存成檔案
② 從輸出往回追挑一行看不懂的輸出，找出是哪段程式印的log 裡的 Loading driver at 0x...，用 grep -rn 在 edk2 原始碼找到它
③ 卡住才往下挖一層看不懂程式碼時，才去讀需要的那一章；挖到能解釋那一行就停看到 gBS->LocateProtocol(...) 看不懂 → 讀 K&R 5.11 函式指標、6.2 結構指標
④ 改它、弄壞它改一個地方，預測會發生什麼，再驗證在 DXE driver 的 entry point 加一行 DEBUG，或故意回傳錯誤，看開機流程怎麼變
⑤ 不看筆記講一遍螺旋結束時，對著空白紙畫圖、講給別人聽，再寫成 blog畫出 SEC→PEI→DXE→BDS，並說明每一段在 log 裡長什麼樣子

問題清單（question backlog）

  • 每次卡住，就在問題清單記一行：問題、在哪裡遇到、目前的猜測
  • 解決時補上答案，以及是哪本書的哪一節解答的
  • 沒有馬上需要的問題先放著，不要為了它岔出去（這是 top-down 最容易失控的地方）
  • 建議放在 career/notes/questions.md，跟 K&R.html 一樣是私人筆記

每週節奏

  • 週一、三、四晚上（1.5 小時 ×3）：主軌，做當前螺旋的成品
  • 週二晚上（1.5 小時）：補強軌，K&R／CS:APP 加習題，用 career/C/serve.sh 跑
  • 週六（5–6 小時）：前 4 小時主軌深度工作，最後 1–2 小時補強軌或整理問題清單
  • 週日（0–2 小時）：Rust 輕量練習，或休息

3. 伺服器的六層地圖

從最上面往下挖。左邊是層，右邊是在哪個螺旋碰到它。每完成一個螺旋，就在這張地圖上多點亮一層。

層這一層在做什麼我會碰到的東西語言螺旋
L1 管理介面從外部查詢、控制伺服器Redfish、IPMI、SEL／SDR、韌體更新（UpdateService）PythonS0、S1
L2 作業系統看到的硬體Linux 開機後怎麼認識硬體lspci、dmidecode、acpidump、sysfs、PCIe config space、dmesgPython、CS1
L3 開機韌體（觀察）OS 之前誰在做事、做了什麼OVMF debug log、SEC／PEI／DXE／BDS、UEFI Shell、memory map、ACPI tablesCS2
L4 開機韌體（修改）自己加功能進韌體DXE driver、protocol、UEFI variable、HII Setup 頁、SSDT、coreboot、真機燒錄C、ASLS3
L5 BMC 內部L1 的 Redfish 背後是怎麼實作的bmcweb、D-Bus、phosphor 感測器、sdbusplus、Yocto／bitbake、RAS、PCIe AERC++S4
L6 最底層CPU 通電後的第一條指令reset vector、real mode、GDT、protected／long mode、E820、x86 組語C、NASMS5

注意 L5 排在 L4 之後：BMC 雖然在 L1 就碰到，但它的內部是 C++ 加 Linux 加 D-Bus，等 C 和開機流程有基礎後再拆比較順。L6 放在最後當作收尾，到那時「OVMF 的 SEC 之前發生了什麼」會是一個自然冒出來的問題。
